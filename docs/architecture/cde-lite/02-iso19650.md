# 02: ISO 19650, and What Compliance Can Mean in Software

Part of the [cde-lite research set](index.md). Research, not a proposal.

## 1. The four container states

ISO 19650 organises a CDE around **information containers** moving through four
states. These are the backbone of the data model:

| State | Meaning | Who sees it |
| --- | --- | --- |
| **Work in progress** | The task team is still developing it | The originating task team only |
| **Shared** | Issued to other task teams, non-contractual | The delivery team |
| **Published** | Authorised and accepted, contractual | The appointing party and the delivery team |
| **Archived** | Superseded, retained for audit | Retained, not current |

Two properties of this model matter more than the list:

- **Transitions are gated, not free.** Work in progress → Shared requires a
  check by the task team. Shared → Published requires review and authorisation
  by the lead appointed party. A CDE that lets a client `PATCH` a state field is
  not implementing 19650; it is storing a label.
- **Nothing is deleted.** Superseded containers are archived and remain
  retrievable. This is an audit requirement, and it is also exactly what a
  content-addressed, append-only history gives for free
  ([`03-version-control.md`](03-version-control.md)).

## 2. The three metadata attributes

The standard series recommends three attributes on every container, and these
are the fields `01`'s untyped metadata bag cannot represent:

1. **Status (suitability)** — what the container is fit to be *used for* now.
2. **Revision** — which issue of the container this is.
3. **Classification** — what kind of thing it is.

The distinction between *state* and *suitability* is worth stating because it is
routinely collapsed: the **state** says where the container is in the workflow;
the **suitability code** says what a recipient is permitted to rely on it for.
Two containers can both be Shared while one is for coordination and the other
only for reference.

## 3. Suitability codes — and why they must be configurable

The commonly used code set:

| Code | Suitable for |
| --- | --- |
| `S0` | Work in progress — not issued |
| `S1` | Coordination |
| `S2` | Information / reference |
| `S3` | Review and comment |
| `S4` | Stage approval |
| `S6`, `S7` | Authorisation stages |
| `A…` | Published and authorised — contractual |
| `B…` | Published with comments |

**This table is not in the core international standard.** It comes from
national annexes, and it varies between them and between appointing parties'
own information protocols.

So the design consequence is firm: **the code table is project configuration,
not an enum in the source.** cde-lite should ship the set above as a seeded
default, let a project replace it, and validate transitions against *the
project's* table. Hard-coding it would make the product wrong outside one
jurisdiction, and silently wrong — the worst kind, because the labels would
still render.

What *is* fixed and can be modelled structurally: that a code exists, that it
has a human-readable meaning, that it is attached to a container version, and
that moving between two codes may require an authorisation event.

## 4. Container naming

19650 expects a structured container identifier — project, originator, volume or
system, level or location, type, role, and number — with the field definitions
again coming from the national annex or the project's information protocol.

Design position: **parse and validate, do not impose.** cde-lite should accept a
per-project naming convention as a pattern with named fields, validate container
names against it, expose the parsed fields as queryable metadata, and report a
non-conformant name as a finding rather than refusing the upload. Refusing
would make the system unusable during the mobilisation period when conventions
are still being agreed, which is exactly when teams need somewhere to put files.

This mirrors a rule the export work already follows: report a finding, do not
fabricate or block.

## 5. What this means for the data model

The minimum shape, stated as fields rather than as a schema:

- **Container** — stable identity, project, name (with parsed convention
  fields), classification, current state.
- **Container version** — content digest, parent version, suitability code,
  revision code, originator, creation time, acceptance record if any.
- **Transition** — from state, to state, actor, timestamp, the gate that
  authorised it, and the checks that passed.
- **Audit entry** — append-only, covering every state change, access grant,
  download and acceptance.

Three observations about this shape:

- **The version carries the suitability code, not the container.** A container's
  history is a sequence of issues at different suitabilities; collapsing the
  code onto the container loses the fact that revision P02 was issued S3 and
  P03 was issued S4.
- **Acceptance is a record, not a flag.** "Who authorised this, when, against
  which requirements, and what did the checks say" is the audit question, and a
  boolean cannot answer it.
- **The digest makes archival honest.** If a version's identity is its content,
  an archived container cannot be quietly altered, and a re-issue of identical
  content is visible as such.

## 6. Where IDS fits, and why it is the strongest card

ISO 19650 requires **exchange information requirements** — what the appointing
party needs delivered, in what form. In practice these are usually prose in a
PDF, checked by eye.

IDS (Information Delivery Specification) is the machine-readable form of exactly
that. This repository already parses and validates it, every facet and
constraint type, in `packages/ids`.

So the acceptance gate writes itself: **a container version cannot transition to
Published unless it passes the project's IDS**, and the validation report is
attached to the acceptance record as evidence. That turns a manual review step
into a reproducible one, and it is the single most defensible feature in this
whole research set — it is standards-based, it is already implemented, and no
mainstream CDE does it at the gate.

The honest limit: IDS checks *information presence and value constraints*. It
does not check geometry correctness, coordination, or whether the model is any
good. It is a necessary gate, not a sufficient one.

## 7. The limit of the word "compliance"

**ISO 19650 compliance is a property of an organisation's processes, not of a
piece of software.** The standard governs how a delivery team plans, produces,
checks, approves and archives information. Software can make conformant
behaviour easy, record evidence that it happened, and make non-conformant
behaviour visible — it cannot confer compliance.

This matters beyond pedantry, for two reasons:

- A deployment can be fully 19650-*capable* and used in a way that is not
  compliant: codes applied by habit, gates clicked through, checks not run.
- Claiming "ISO 19650 compliant" as a product attribute invites an expectation —
  and in some procurement contexts an obligation — that cannot be met by a
  codebase.

The defensible claim is narrower and still strong: cde-lite implements the
**information container model, state transitions, suitability and revision
metadata, gated authorisation and the audit trail** that ISO 19650 describes,
and produces the evidence an auditor would ask for. That sentence should be the
ceiling of any user-facing claim, and `index.md` §9 records it as a standing
risk.

## 8. What was not researched here

- **19650-3 (operational phase)** and **19650-5 (security-minded approach)**.
  The second is directly relevant to a multi-tenant platform and is unexamined
  here; `05-multitenancy.md` reasons about isolation from first principles
  rather than from that part of the standard.
- **Revision code grammars.** The sources consulted describe revision as a
  recommended attribute without pinning a format, so cde-lite should treat it as
  a validated string with a per-project pattern, the same as container naming.
- **The relationship between suitability codes and contractual effect**, which
  is a legal question and not one to resolve in a design document.

Sources consulted: the UK BIM Framework guidance on 19650 information
management and on facilitating the CDE workflow, the national annex guidance,
and secondary explanations of the status code set. Where they disagreed on the
exact code table, §3's conclusion — make it configurable — is the response.
